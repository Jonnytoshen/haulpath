## 环境与边界

本轮使用 macOS arm64、Node.js 24.21.0、pnpm 12.10.1、项目 Playwright 1.62.1 和系统 Google Chrome；浏览器视口为 1600×1050。每个自动化场景启动真实 Next.js 本机服务，使用独立临时 SQLite；下载真实 `.xlsx` 并通过 ExcelJS 读取，不替换应用自身的接口、数据仓储或工作簿生成。

只有高德 HTTP 服务与浏览器地图 SDK 是可控替身：后端测试显式设置 `ZHONGTU_TEST_MODE=1`，高德地址仅指向 loopback；前端仅拦截外部高德 SDK 的加载。替身将实际收到的编号点位、每段折线和聚合点数量暴露为可观察数据。这证明应用传入的内容与方案一致，不能证明真实地图、搜索或路况效果。

**真实高德 Web 服务 Key、JS Key、安全密钥当前未配置，真实服务联调未执行。未校验重卡限高、限重及货车限行。**

## 完整用户闭环

通过真实浏览器创建项目与三站线路，上传 UTF-8 CSV、预览并确认 3 行有效点，随后逐个从项目点库选入线路。初次规划返回 2 个区间，总里程 2.468 km；更改为高速优先后显示待重算、退出旧折线并清空当前里程。再次规划成功，地图恢复 2 段折线，总里程 4.690 km。

从浏览器下载当前线路实际工作簿：固定双表、公里数值单元格、`0.000` 格式、高速优先和累计距离均对应新方案。外部替身共收到 4 次区间请求，导出未额外调用规划。已有测试另覆盖失败保留完整结果、输入/任务迟到竞争、三种偏好、整数米合计、导入失败不半写入、跨项目归属及北京时间输出。

## 代表性负载

在单个项目中，浏览器实际导入 **1,000 个合法 GCJ-02 点位**，通过公开 HTTP 创建 **100 条线路**，其中一条含 **20 个有序点位**，另外 99 条保留草稿。浏览器能筛选第 1,000 个点位、切换线路、上移/下移并恢复顺序；地图聚合接收 1,000 点，当前线路显示 20 个编号点位。

点击规划后显示 19 个区间进度，完成 19 段折线。替身为每段第一方案返回 1,234 米，另提供不同的第二方案以验证选择；结果为 **23,446 米 / 23.446 km**。项目实际导出含 100 行总览和 19 行区间明细，草稿总览保留、当前距离留空。停止并重启本机服务后，公开接口及新的浏览器上下文仍读取到 100 条线路、1,000 库点和完整成功方案，打开不触发重算。

以下为一次串行全套运行中的本机观测，包含真实页面操作和文件读取；不是性能承诺，也不是业务硬上限：

| 操作 | 耗时 |
| --- | ---: |
| 1,000 点预览后的确认导入至页面完成 | 1,025 ms |
| 并行公开接口读取 100 线路与 1,000 点库 | 11 ms |
| 已编译开发服务中刷新至线路及聚合层就绪 | 212 ms |
| 20 点点击规划至完整结果可见 | 1,373 ms |
| 100 线路项目导出至实际工作簿解析完成 | 758 ms |

高德替身每段等待约 30 ms；这些数字不代表真实高德延迟。典型规模不是拒绝更大数据量的限制。

## 备份与恢复

使用系统 SQLite CLI 3.54.0 实际执行文档 `.backup`：备份时本机服务仍运行、源 `-wal` 存在；独立备份的只读不可变 URI 完整性检查为 `ok`。备份之后通过公开接口新增一条项目，再停止服务，把原数据目录（包括 sidecar）整体隔离，复制备份并重新启动。

恢复后从公开 HTTP 验证：原项目、项目点库和完整路线方案与备份前一致，备份后的新增项目不存在，旧库仍在回退目录。本轮不新增维护 CLI，不直接读私有 SQL 验证业务内容。操作命令及自定义路径注意事项见[运行维护](operations.md)。
