# 逐车运输日计划

规划方案的「每日计划」提供运输、车辆电量、站内周转和共享电源四种试算。运输试算核对时间、载荷与需求完成量，车辆电量试算在已选固定布局中安排换电访问，站内周转试算进一步核对工位、满电库存和站内充电。共享电源试算进一步联合约束同源站点的充电功率。**24 小时周期仍待校核。四个阶段都不能发布完整物理可行候选。未校验重卡限高、限重及货车限行。**

## 输入和计算依据

先确认闭合运输循环，录入运输需求、可用车辆与运营时间模板，再选择场地及接电关系已确认的固定布局。为当前输入版本显式完成道路准备后即可发起试算。任务保存当时实际采用的道路、上下文和修订号，运行期间使用这份快照。道路采用优先级见[有向道路资料](directed-road-data.md)。

运输就绪检查载重、有效基准起点、班次、装卸耗时与来源。业务区间使用方向、位置和偏好仍有效的实测时间覆盖业务速度，实测耗电的载重依据单独校核。跨线接续及归位使用业务速度，缺失时列出缺口。排程使用车辆身份池中前 `count` 辆。运输试算可以在电池、能耗或财务资料仍待完善时运行。

一个车次完整经过某个循环的固定位置顺序，并返回该循环起点。需求可拆分，同一车次按每个需求经过的区间占用载重，已卸货腾出的容量可供后续装货。每个有作业的点位分别计一次装货和卸货的模板耗时，先卸后装。末次装载剩余需求。吨位累加使用补偿求和，在数值的机器精度范围内消除残差，避免残差额外占用一个车次。

有限贪心构造在可用车辆、班次和循环中选择能够完成并预留归位时间的最早结束车次。完成循环后可跨线接续，班次结束前回基准循环起点；跨线接续和归位的有向道路距离与时间均进入事件及汇总。班次间空档保持在基准起点，无工作事件。算法版本、种子和时限随任务保存；种子影响循环平局顺序，默认 1。默认最长 10 分钟，可设 5–120 分钟，有限构造完成后提前结束。该构造不保证最优，运量缺口不证明无解。

生成器与校验器分离。校验器根据输入、事件及车次重新检查可用车辆、位置连续性、完整循环、装卸顺序、每段载重、需求完成量、同车事件互斥、班次与归位、距离和时间依据。只有通过运输校验的完整结果才发布。

## 换电绕行与车辆电量

- 首日每辆执行运输的车辆从统一电池的 100% SOC 出发，每次换入电池也按 100% 计算。车辆在事件间和班次间连续保留电量，直到收车归位。结果保留首尾电量及这一阶段性假设。可重复的跨日初态由周期校核另行求解。
- 直达业务区间的有效有向实测按实际载荷在空载与满载耗电间插值，单位为整段 kWh。模板以相同载荷比例插值后乘以实际道路公里数。失效实测使用有效模板，绕行、跨线接续及归位也使用模板，接续及归位按空载。行驶段耗电按该段均匀下降，以段末电量核对全段安全余量。
- 每次业务区间可选择直达或插入一次换电。使用固定布局内同规格站型及分别准备的有向进、出站道路。两段行驶分别按业务速度计时，额外距离和时间以同方向直达道路及其原计时（含有效实测）为比较基准，小于零的差额按零计。启用的限额同时满足，留空表示不限，零表示不允许增加。
- 换电安排在服务窗口内。为等到服务窗口开放而发生的等待、换电服务和额外行驶均占用当班作业时间，且要求在班次内完成原业务序列和归位。此阶段只按服务窗口安排等待，工位排队和可用电池在站内周转试算中校核。
- 车辆电量试算以本次构造的运输车次、载荷和班次为基础，沿每辆车的业务顺序搜索可安全到达的换电访问，包括提前换电。结果分别保留直达运输基线及实际换电时间轴。校验器从固定快照和基线事件复核有向道路、服务窗口、耗电、安全余量、载荷与班次归位。当前搜索保持车次和班次分配，某次试算失败不证明该布局无解。

保存限额会形成新的输入版本。按界面提示为该版本完成道路准备后，可利用缓存资料发起试算。冻结、复制、比较与历史快照遵循统一输入版本契约。

## 站内周转

- 在同一份任务快照中构造运输和车辆电量基线，再保留其车次、班次和换电访问，按各车实际到站时刻处理，平局按计划车辆顺序。每个站独立使用其所选站型的资源。工位占用从服务开始到结束，结束时释放。工位、满电库存及服务窗口都可造成等待；等待传入同班次后续业务和归位。阶段内不另换站址或重排车次，失败仅表示本次未找到通过校核的安排。
- 代表日零点时各站配置的备电池全部按满电可用，车辆的首日初始电量另计。换电开始领用满电电池，结束才接收换下的电池。同刻释放工位、充电完成或回收满电电池后，可供接续服务使用。用换电事件标识关联回收和充电，每份满电库存只领用一次。
- 单电池以统一规格给定的电网侧等效功率连续充到满电。补入电量为容量减去回收电量，购电量为补入电量除以效率，充电时长为购电量除以功率。例如容量 100 kWh、回收电量 60 kWh、等效功率 50 kW、效率 0.8 时，连续充电 60 分钟，购电 50 kWh，补入 40 kWh。充电前可等候可用充电位、本地功率与完整充电窗口；站型总功率和站址可用功率分别约束同时充电，站点之间的电源占用在后续共享电源阶段联合校核。
- 台账截止于午夜或在用车辆组最晚班次结束，取较晚时刻。截止前可启动充电，完整窗口允许时可跨午夜及越过台账截止时刻连续完成。截止库存分别列满电、待充、在充数量；充电事件列完整任务的能量，有起止时刻才计为已安排。首尾库存及车辆电量留待 24 小时周期校核。
- 生成完成后，独立校验器根据固定快照复核实际车辆事件、班次和归位，再按车辆换电、回收和充电时刻重放站内账目，核对本地容量及库存守恒。站址、车辆和到站时刻随失败原因显示；失败不替换已有完整阶段结果。

## 共享电源与分时购电

- 共享身份使用任务快照内采用的电源 `powerSources[].id`，容量取对应的 `point.availableCapacityKw`，不按名称、站型或项目源资料的最新值分组。站型总功率、站址接电功率及充电位继续分别限制每站。
- 延续站内阶段的车次、班次、换电访问及实际到站顺序；同刻按计划车辆顺序处理。安排换电时，为返回电池预订最早可容纳完整连续充电的区间，同时满足本站资源、完整充电窗口与共享电源容量。所有预订均不可抢占，等待发生在开始充电前；充满时刻决定后续满电库存，库存等候继续传入实际车辆事件和归位。
- 跨站回收顺序可能与到站处理顺序不同。共享日历检查完整预订区间，允许后处理的回收电池填入未来预订前的空档；不能用一个全局最晚释放时刻代替日历。已预订区间不再重排，因此本次构造失败不证明其他错峰、换电或车次安排无解。种子、阶段算法版本及任务快照可追溯；本票未按分时电价选择充电时段。
- 例如两站各需一段 120 kW、72 又 7/9 分钟的连续充电，共享容量 200 kW、窗口 98 分钟。窗口能提供 326 又 2/3 kWh，大于两次充电所需的 291 又 1/9 kWh，但两段同时充电需 240 kW、串行又超出窗口。必须保留待充与库存瓶颈，不能用总能量代替峰值校核。
- `result.sharedPower` 保存每个实际采用电源的容量依据、完整充电预订峰值和按时间分布的实际购电账目。`sources[].intervals` 覆盖 `[0, horizonMinute)`，按充电起止和午夜分段，含零占用区间；各行列电源与站点的恒定电网侧功率和购电量（功率乘以区间小时数）。后续电价核算可继续按价段求交，不以日总电量代替功率时序。
- 购电统计只计完整充电区间与统计范围的交集。尚未开始的待充需求不计购电；跨截止充电的完整起止、需求电量和补入量仍保留在站内账目。电源峰值按全部完整预订校核，包括截止之后。车辆组最晚班次结束晚于午夜时沿用该截止时刻；这不是已求得的 24 小时周期边界。
- 独立发布校验先重放车辆、工位、连续充电、站内功率与库存守恒，再跨站检查所有充电开始边界的瞬时共享功率；另按每段充电与统计区间的交集核对分时购电、站点归属、峰值及汇总。无需求消耗的待充/在充库存可作为首日阶段账目保留，不表示恢复初态；周期状态始终为未校核，完整物理可行性仍未建立。

## 公开接口与生命周期

接口前缀为 `/api/projects/:projectId/scenarios/:scenarioId/daily-transport`。

| 方法与后缀               | 行为                                                                                             |
| ------------------------ | ------------------------------------------------------------------------------------------------ |
| `GET /`                  | 当前输入版本、运输、车辆电量及站内周转（含共享电源）就绪缺口、任务摘要及最近完成的阶段结果       |
| `PUT /`                  | `{expectedRevision, swapDetourLimits: {maxExtraMeters, maxExtraMinutes}}` 保存绕行限额并返回方案 |
| `POST /`                 | `{expectedRevision, config?: {stage?, seed?, maxRuntimeMs?}}` 创建持久任务并返回 202             |
| `GET /:taskId`           | 读取本项目、本方案下任务及固定输入、进度和结果                                                   |
| `GET /:taskId?summary=1` | 读取用于轮询的任务状态及进度，省去快照和结果                                                     |
| `POST /:taskId/stop`     | 停止该任务并返回方案任务视图                                                                     |

`stage` 接受 `transport`（默认）、`vehicle-energy` 、`station-turnover` 和 `shared-power`。省略阶段的历史任务按运输试算读取。限额为非负整数米或非负分钟数，两项各可为 `null`。两个限额均未启用时，上下文可省略 `swapDetourLimits`。相同输入不增加版本，通用方案接口不能直接修改限额。

车辆电量试算在 `result.vehicleEnergy` 保存电池依据、逐车行驶里程与工时、实际事件和 SOC 以及后续校核状态。站内周转试算另在 `result.stationTurnover` 保存各站初态、截止库存、换电服务和恒功率充电事件；`result.vehicleEnergy` 保存计入等待后的实际车辆时间轴。共享电源阶段另存 `result.sharedPower`，并将 `result.vehicleEnergy.sharedPowerStatus` 标为 `checked`。旧阶段和历史任务继续保留原校核状态。原运输字段仍描述直达运输基线。校验或搜索失败的任务只保存状态和具体原因，最近完成的阶段结果仍可读取。

应用内仅一个运输计算 Worker 运行，其他运输任务排队；道路准备使用其既有独立队列。启动请求不等待算法完成，页面关闭不停止任务。主线程负责 HTTP、SQLite 和任务发布，纯计算在 Worker 中执行。输入版本变化、冻结、停止或超时后，迟到消息不能发布；复制方案不继承任务或正式结果。只改方案名称不使任务失效。

任务与结果以项目、方案、输入版本及任务身份共同归属，不能通过通用 `context.results` 写成正式结果。失败、停止、超时保留此前完整结果；页面标明其输入版本。服务首次打开 SQLite 后把遗留排队及运行任务标为中断，用户重新试算；不自动恢复指令。数据库 schema 6 从旧版本顺序迁移，保留既有资源及道路任务。

## 页面核对

「每日计划」显示运行状态、算法依据、需求完成量与缺口。缺口分别说明从基准起点直接往返的一趟车次放不进现有班次，或当前构造未安排完。逐车时间轴与事件表列出运输、装卸、跨线空驶和归位，车次区间表列出载重、道路里程、时间及实测或速度来源。循环位置带顺序编号，便于核对同名点位。历史结果按所属输入版本展示。车辆电量结果逐车列出实际行驶、换电、SOC 变化、安全余量及收车电量。站内周转结果按站址展示满电库存、工位、等待原因、充电窗口及购电和补入电量。共享电源结果先显示容量、峰值、各站占用与分时购电，再核对各站库存和连续充电。共享功率等待与窗口冲突单列，周期状态独立显示。

## Worker 交付

应用启动适配层在开发启动与生产构建时，将应用 Worker 和引用的领域源码打包成 `apps/web/.haulpath-workers/daily-transport.cjs`；开发每次启动试算还在独立进程重建，以采用最新领域源码。领域包仍直接消费 TypeScript，不增加预构建。普通生产启动使用构建产物，standalone tracing 和 Docker 显式携带该文件。

产物目标为 Node 22.12 的 JavaScript，不要求 Node 直接读取 TypeScript。[Node Worker 文档](https://nodejs.org/download/release/v22.12.0/docs/api/worker_threads.html)与 [esbuild Node 平台选项](https://esbuild.github.io/api/#platform)是实现依据。实际运行范围与未验证边界见[验收记录](acceptance.md)，不得以加载测试代替整套最低 Node 验收。
